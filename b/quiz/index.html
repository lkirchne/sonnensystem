01

Vererbung (Inheritance)

Was ist Vererbung?

Vererbung ist ein Mechanismus, bei dem eine Klasse (Subklasse) Eigenschaften und Methoden von einer anderen Klasse (Superklasse) übernimmt. Die Subklasse erweitert oder spezialisiert die Superklasse.

In unserem Sonnensystem-Projekt haben wir eine Vererbungshierarchie aufgebaut:

public class Himmelskoerper { private String name; private double durchmesser; private double geschwindigkeit; public void bewegung() { // Berechnet Bewegung auf Orbit } } public class Planet extends Himmelskoerper { // Erbt ALLE Attribute und Methoden von Himmelskoerper } public class Stern extends Himmelskoerper { // Erbt ebenfalls von Himmelskoerper }

Warum Vererbung?

Vererbung löst ein wichtiges Problem: Code-Duplikation vermeiden. Ohne Vererbung müssten wir in jeder Klasse (Planet, Stern, Mond, Komet...) dieselben Attribute und Methoden neu schreiben. Mit Vererbung definieren wir gemeinsame Eigenschaften nur einmal in der Oberklasse.

Die "ist-ein"-Beziehung
Vererbung modelliert immer eine "ist-ein"-Beziehung: Ein Planet IST EIN Himmelskoerper. Ein Stern IST EIN Himmelskoerper. Wenn diese Beziehung nicht passt (z.B. "Ein Auto IST EIN Motor" – falsch!), sollte man keine Vererbung verwenden, sondern Komposition ("Ein Auto HAT EINEN Motor").
Planet und Stern erben ALLE Attribute (name, durchmesser, geschwindigkeit, etc.)
Planet und Stern erben ALLE Methoden (bewegung(), getter, setter)
Das Schlüsselwort extends definiert die Vererbungsbeziehung
Java unterstützt nur Einfachvererbung (eine Klasse kann nur von einer anderen erben)
Subklassen können geerbte Methoden überschreiben (@Override), um spezielles Verhalten zu definieren

02

Polymorphie

Was ist Polymorphie?

Polymorphie (griechisch: "Vielgestaltigkeit") bedeutet, dass Objekte verschiedener Klassen über eine gemeinsame Schnittstelle angesprochen werden können. Ein Objekt kann sich je nach seinem tatsächlichen Typ unterschiedlich verhalten.

Das Mächtige an Polymorphie: Wir können alle Himmelskörper gleich behandeln, obwohl sie verschieden sind!

// Array vom Typ Himmelskoerper kann verschiedene Objekte speichern Himmelskoerper[] objekte = new Himmelskoerper[10]; objekte[0] = new Stern(); // Ein Stern ist ein Himmelskoerper objekte[1] = new Planet(); // Ein Planet ist ein Himmelskoerper objekte[2] = new Planet(); // Noch ein Planet // Alle können gleich behandelt werden: for (Himmelskoerper h : objekte) { if (h != null) { h.bewegung(); // Funktioniert für alle! } }

Dynamische Bindung (Late Binding)

Ein wichtiges Konzept hinter Polymorphie ist die dynamische Bindung: Der Compiler weiß zur Compile-Zeit nicht, welche konkrete Methode aufgerufen wird – das entscheidet sich erst zur Laufzeit basierend auf dem tatsächlichen Objekttyp.

Himmelskoerper h = new Planet(); // Variable vom Typ Himmelskoerper h.zeichne(g); // Welche zeichne()-Methode wird aufgerufen? // Antwort: Die von Planet! Nicht die von Himmelskoerper. // Der tatsächliche Typ des Objekts (Planet) entscheidet, // nicht der deklarierte Typ der Variable (Himmelskoerper).
Warum ist das wichtig?
Durch dynamische Bindung können wir Code schreiben, der mit zukünftigen Klassen funktioniert, die wir noch gar nicht kennen! Wenn jemand später eine Klasse Komet hinzufügt, die von Himmelskoerper erbt, funktioniert unsere Schleife automatisch auch für Kometen – ohne eine einzige Zeile zu ändern.
Eine Variable vom Typ Himmelskoerper kann auch Planet- oder Stern-Objekte speichern
Alle Objekte im Array können mit denselben Methoden angesprochen werden
Dynamische Bindung: Erst zur Laufzeit wird entschieden, welche Methode aufgerufen wird
Polymorphie ermöglicht flexiblen, erweiterbaren Code – neue Klassen fügen sich nahtlos ein

03

Datenkapselung (Encapsulation)

Was ist Datenkapselung?

Datenkapselung bedeutet, dass Attribute einer Klasse vor direktem Zugriff von außen geschützt werden. Der Zugriff erfolgt nur über kontrollierte Methoden (Getter und Setter).

public class Himmelskoerper { private String name; // Geschützt! private double geschwindigkeit; // Geschützt! // Getter: Wert lesen public String getName() { return name; } // Setter: Wert setzen mit Validierung! public void setGeschwindigkeit(double g) { if (g >= 0) { // Nur positive Werte erlaubt this.geschwindigkeit = g; } } }
Sichtbarkeit Zugriff Verwendung
private Nur innerhalb der eigenen Klasse Für Attribute (Schutz der Daten)
public Von überall Für Getter/Setter und öffentliche Methoden
protected Eigene Klasse, Subklassen & gleiches Package Wenn Subklassen direkten Zugriff brauchen
Private Attribute verhindern ungültige Werte (z.B. negative Geschwindigkeit)
Getter erlauben kontrolliertes Lesen der Werte
Setter können Eingaben validieren bevor sie gespeichert werden
Die interne Implementierung kann geändert werden, ohne dass andere Klassen angepasst werden müssen
Wichtig: Private Attribute und Vererbung
Subklassen wie Planet erben zwar die privaten Attribute von Himmelskoerper (sie sind Teil des Objekts im Speicher), können aber nicht direkt darauf zugreifen. Ein this.name = "Erde" in der Klasse Planet würde einen Fehler werfen! Stattdessen muss Planet die Getter und Setter der Oberklasse nutzen: this.setName("Erde"). Das ist gewollt – so bleibt die Validierung erhalten.

04

Abstrakte Klassen

Neues Konzept
Abstrakte Klassen erweitern das Konzept der Vererbung und ermöglichen noch besseres Design.

Was ist eine abstrakte Klasse?

Stell dir vor, du sollst ein "Tier" zeichnen – nicht einen Hund, nicht eine Katze, sondern einfach nur "ein Tier". Das geht nicht wirklich, oder? Ein Tier ist ein Oberbegriff, keine konkrete Sache. Genauso verhält es sich mit Himmelskoerper in unserem Projekt.

Eine abstrakte Klasse ist eine Klasse, von der man keine Objekte erstellen kann. Sie dient als gemeinsame Vorlage für andere Klassen. Das Schlüsselwort abstract markiert sie als "unvollständig" – sie braucht Subklassen, die sie vervollständigen.

Alltagsbeispiel
Denke an den Begriff "Fahrzeug": Du kannst kein "Fahrzeug" kaufen – du kaufst ein Auto, ein Fahrrad oder einen Bus. "Fahrzeug" ist nur der Oberbegriff, der beschreibt, was alle gemeinsam haben (sie bewegen sich, haben eine Geschwindigkeit). Aber jedes konkrete Fahrzeug sieht anders aus und funktioniert anders.

Warum Himmelskoerper abstrakt machen?

In unserem Sonnensystem-Projekt gibt es keine "echten" Himmelskörper – es gibt nur konkrete Typen: Planeten, Sterne, Monde. Ein Objekt vom Typ Himmelskoerper direkt zu erstellen wäre problematisch:

Wie soll ein "allgemeiner Himmelskoerper" gezeichnet werden? Als Kreis? Als Stern? Wir wissen es nicht!
Welche Farbe hat er? Welche Größe ist typisch? Es gibt keine sinnvollen Standardwerte.
Wenn jemand versehentlich new Himmelskoerper() schreibt, ist das ein Programmierfehler – den wollen wir verhindern.
// VORHER: Normale Klasse – erlaubt unsinnige Objekte public class Himmelskoerper { ... } Himmelskoerper h = new Himmelskoerper(); // Kompiliert, aber macht keinen Sinn! // NACHHER: Abstrakte Klasse – der Compiler schützt uns public abstract class Himmelskoerper { ... } Himmelskoerper h = new Himmelskoerper(); // FEHLER! Der Compiler sagt: "Geht nicht!" Himmelskoerper p = new Planet(); // OK! Planet ist konkret.

Abstrakte Methoden: Der "Vertrag"

Eine abstrakte Klasse kann abstrakte Methoden enthalten. Das sind Methoden ohne Implementierung – nur die Signatur (Name, Parameter, Rückgabetyp). Sie sagen: "Jede Subklasse MUSS diese Methode selbst implementieren!"

public abstract class Himmelskoerper { private String name; private double durchmesser; private double geschwindigkeit; protected double x, y, winkel, orbitRadius; // Koordinaten für Bewegung // KONKRETE Methode: Hat einen Rumpf { ... } // Alle Himmelskörper bewegen sich gleich → einmal schreiben, überall nutzen public void bewegung() { winkel += geschwindigkeit; x = zentrum_x + orbitRadius * Math.cos(winkel); y = zentrum_y + orbitRadius * Math.sin(winkel); } // ABSTRAKTE Methode: Kein Rumpf, nur Semikolon! // Jeder Himmelskörper zeichnet sich anders → Subklassen müssen das selbst regeln public abstract void zeichne(Graphics g); }
Die Regel für abstrakte Methoden
Wenn eine Subklasse von einer abstrakten Klasse erbt, MUSS sie alle abstrakten Methoden implementieren. Tut sie das nicht, muss sie selbst als abstract deklariert werden. Der Compiler erzwingt das – es gibt kein Entkommen!

Subklassen vervollständigen die Vorlage

public class Planet extends Himmelskoerper { @Override // Sagt: "Ich implementiere hier eine geerbte/abstrakte Methode" public void zeichne(Graphics g) { // Planet wird als gefüllter Kreis gezeichnet g.setColor(farbe); g.fillOval((int)x, (int)y, durchmesser, durchmesser); } // bewegung() muss NICHT überschrieben werden – Planet erbt sie einfach! } public class Stern extends Himmelskoerper { @Override public void zeichne(Graphics g) { // Stern wird anders gezeichnet (z.B. mit Strahlen) g.setColor(Color.YELLOW); g.fillOval((int)x, (int)y, durchmesser, durchmesser); // ... Strahlen zeichnen ... } }

Was resultiert aus abstrakten Klassen?

Sicherheit: Es kann kein "unvollständiges" Himmelskoerper-Objekt erstellt werden
Vertrag: Jede Subklasse MUSS die abstrakte Methode zeichne() implementieren
Wiederverwendung: Gemeinsamer Code (z.B. bewegung()) wird nur einmal geschrieben
Klarheit: Es ist sofort erkennbar, dass Himmelskoerper nur eine Vorlage ist
Polymorphie: Wir können weiterhin Himmelskoerper[] verwenden und alle Objekte einheitlich zeichnen
Wichtig zu beachten
Wenn eine Klasse auch nur EINE abstrakte Methode enthält, MUSS die Klasse selbst als abstract deklariert werden. Eine Subklasse, die nicht alle abstrakten Methoden implementiert, muss selbst auch abstract sein.

05

Interfaces

Was ist ein Interface?

Ein Interface ist ein "Vertrag", der festlegt, welche Methoden eine Klasse implementieren muss. Im Gegensatz zu Vererbung kann eine Klasse mehrere Interfaces implementieren.

Während Vererbung eine "ist-ein"-Beziehung beschreibt, beschreibt ein Interface eine "kann"-Beziehung bzw. eine Fähigkeit: Die Klasse Sonnensystem KANN auf Actions reagieren (ActionListener).

// Das Interface ActionListener (von Java) public interface ActionListener { void actionPerformed(ActionEvent e); // Muss implementiert werden! } // Unsere Klasse implementiert das Interface public class Sonnensystem implements ActionListener { @Override public void actionPerformed(ActionEvent e) { // Diese Methode wird bei jedem Timer-Tick aufgerufen for (Himmelskoerper h : objekte) { if (h != null) { h.bewegung(); } } zeichenflaeche.repaint(); } }

Mehrfachimplementierung

Ein großer Vorteil von Interfaces: Eine Klasse kann mehrere Interfaces implementieren, aber nur von einer Klasse erben. Das ermöglicht flexible Kombinationen von Fähigkeiten.

// Eine Klasse kann mehrere Interfaces implementieren public class Sonnensystem extends JFrame implements ActionListener, MouseListener { // Erbt von JFrame (Fenster) // Kann auf Timer-Events reagieren (ActionListener) // Kann auf Maus-Events reagieren (MouseListener) }
extends (Vererbung) implements (Interface)
Was wird übernommen? Attribute + Methoden (mit Zustand) Methodensignaturen (Vertrag), keine Instanzvariablen
Anzahl möglich? Nur eine Klasse Mehrere Interfaces
Verwendung "ist-ein"-Beziehung "kann"-Beziehung (Fähigkeit)
Gut zu wissen
Seit Java 8 können Interfaces auch Default-Methoden mit Implementierung enthalten. Der wichtigste Unterschied zu Klassen bleibt aber: Interfaces können keinen Zustand (Instanzvariablen) speichern – sie definieren nur, WAS ein Objekt können muss, nicht WIE es intern aufgebaut ist.

Timer & Ereignisgesteuerte Programmierung

Wie funktioniert der Timer?

Ein Timer löst in regelmäßigen Abständen ein Event aus. Die Klasse, die auf dieses Event reagieren soll, muss das Interface ActionListener implementieren.

public class Sonnensystem implements ActionListener { public void urknall() { // Timer erstellen: alle 20ms ein Event Timer timer = new Timer(20, this); timer.start(); } @Override public void actionPerformed(ActionEvent e) { // Wird AUTOMATISCH alle 20ms aufgerufen! for (Himmelskoerper h : objekte) { if (h != null) { h.bewegung(); } } zeichenflaeche.repaint(); // Neu zeichnen } }
Event: Ein Ereignis (Timer-Tick, Button-Klick, Tastendruck)
Listener: Ein Objekt, das auf Events "hört"
Handler: Die Methode, die beim Event ausgeführt wird
this bedeutet "dieses Objekt" – die Sonnensystem-Instanz ist selbst der Listener

Tipp
Verwende Array, wenn die Anzahl der Elemente von Anfang an feststeht.
Verwende ArrayList, wenn Elemente dynamisch hinzugefügt oder entfernt werden sollen.
